# Hollow Knight (ForestDango) Exp 0 v0 protocol

Evaluate one component diagnosis per complete native episode. The primary endpoint is component accuracy on 30 verified interventions, with abstentions and invalid outputs scored as incorrect. Compare `read` and `probe` on the same 40 episodes. The ten no-injection controls measure unsupported component accusations: a control false positive is an asserted component fault without supporting audit evidence (#185). [Issue #185](https://github.com/HectorHHZ/llm-honing/issues/185) · [Exp 0 #174](https://github.com/HectorHHZ/llm-honing/issues/174) · reference: the accepted Griddly Spiders v0 release.

## Collection

Use the full Hollow Knight remake of ForestDango (`Hollow-Knight-Demo`, Unity) with the Honing bridge, as the deterministic development build `linux64_devmode_c` (bridge `{{BRIDGE_VERSION}}`; player binary SHA-256 `{{BUILD_SHA}}`, `Assembly-CSharp.dll` `{{CSHARP_SHA}}`; launch script `hk_fast.sh`: `HONING_FAST=1`, `-batchmode -nographics`, nothing drawn). The same native input gives the same frames on this build. Every developer knob (`HONING_DEV_*`: revive, no damage, skipped fades or death wait) is off in every dataset run, no lookahead or process fork feeds anything the model sees, and the only extra bridge variables are `HONING_FRAME_LOG=1` and `HONING_FRAME_LOG_BOOT=1`, a read-only per-frame state log used for the native replay check (measured inert: a route played with and without it gives identical debug and visible observations). The game, its assets and the build are not included: ForestDango/Hollow-Knight-Demo has no license, so the deterministic build is not redistributable.

The harness is the frozen no-autopilot `v12_standing` (fingerprint `{{HARNESS_FINGERPRINT}}`), a pinned copy with one constant changed for privacy (the local path of the decision model's tokenizer file, now set at run time from the public checkpoint and SHA-256-checked, `{{TOKENIZER_SHA}}`; a strict replay of three recorded development runs of `v12_standing` with the copy gives 511 of 511 requests byte-identical). Each decision is one request with two questions, answered together: `move` (nine raw key combinations: hold left / right / no direction, each with no, a short or a long jump) and `attack` (none, strike forward, up, down, hold focus). The request is plain English text: a fixed briefing, the knight's state (masks, SOUL, standing or in the air, facing), what is on the current screen (ground, ledges, walls, ceiling, enemies, doors, spikes, all as distances in units from the knight) and the harness's memory of the room; every option text says what the keys would lead to by the harness's own forecast. The harness never removes, reorders, ranks or recommends an option, and no skill or reflex acts without the model. The model gets text only, never pixels: what a player sees on the current screen and the HUD, plus the harness's memory of what was seen before (global or debug views are never used). The keys of both answers are held for 13 frames (0.43 s), sent as two or three native windows. The game waits while the model decides.

The clean checkpoint is Laya `convaiinnovations/laya-typed-decisions@1a793eb5` (weights `4fa56de7…`, services 8811 and 8820, identical: the second service re-answered 12 logged requests of the first with largest difference 0.0). The alternate is `jayzou3773/laya-ra2-v33@51d2f5a0` (weights `2ed46ac9…`, service 8812), a Red Alert 2 fine-tune of the same Laya, served by the same server code. Both run on CPU in FP32. The policy is the highest-probability option of each question. The collector checks the served weights SHA-256 before and after each episode, and every reply must pass the response guard before any key is sent; a rejection ends the episode with nothing executed.

One episode ("一局") starts in King's Pass, the game's first area. Its reset procedure is a new game of the build and then the reset group's start prefix: the first k steps of one fixed reference route (9 frames per step, keys given by the script, played through the harness so that its memory includes the way there; the steps are not model decisions and are not rows of the episode). The episode starts at the first model decision after the prefix. It is a **win** when the knight stands (the game's own grounded flag) with its feet within 1.0 unit sideways and 0.3 units in height of the group's waypoint, at the end of any native window; a **loss** at the knight's first death; a **timeout** at {{DECISION_CAP}} model decisions (or {{FRAME_CAP}} native frames from the first decision); leaving King's Pass is **other terminal**. The waypoint of a start is fixed by one rule for all groups: the first place after the start where the reference route stands that is at least 7 units from the start place (straight line) or at a feet height that differs by at least 0.5 units (beyond a jump or a drop). So no waypoint can be reached by one or two plain walking decisions: on the clean pilots one plain walking decision moved the knight at most 3.32 units and two at most 5.72, and plain-walking tests from two climb starts on the build fell off the ledge or stopped at the wall.

The three interventions are persistent for the whole episode, one instance per component:

- Harness (`omit-ground-v1`, #185 "Omit available floor/ground information"): from the first model decision whose clean request describes the ground or ledges (decision 0 at every start), the "Ground: …" and "Ledges near you: …" sentences are left out of the request's "On screen" line; the options, option texts and everything else are unchanged. The collector keeps the logged request and the clean render of the same saved state (`clean_request`); the public observation keeps the true screen. Re-validated offline on recorded development runs of `v12_standing` before the collection: it changes the request from the first model decision in all three.
- Weights (`laya-ra2-v33-v1`): the alternate checkpoint serves both questions for the whole episode. Evidence: the first request identical (byte for byte, same native tick) to one of the matched clean episode of the same reset group whose normalized probabilities differ by more than 0.01 in any option of either question; the same request re-asked on the clean service is kept as well (`weights-reask.jsonl`).
- Controller (`swap-left-right-v1`): after the selection, at every decision whose chosen move holds a direction key, LEFT and RIGHT are exchanged in the native keys sent to the game (jumps, attack and focus unchanged). Every changed window keeps the keys the harness asked for (`intended_action`) next to the keys sent. A legal cooldown ("NOT READY") is never a controller fault.

Validate every attempt against the episode contract (0.2.0) and record all incomplete, untriggered, rejected and unselected attempts. Every attempt was replayed natively: a new game process of the same build fed only the attempt's recorded native input (boot, prefix and episode) reproduced every logged debug state, visible observation and per-frame state record. Use the matched clean result as separate outcome evidence. This v0 collection records per-decision component effects; release-level score drop is untested. The 23 clean pilots, the smoke runs and the fault smokes (2026-11-26) were development data and are outside the scored set.

## Diagnosis

Render `read` inputs from an explicit allowlist of public observations, displayed model requests (rendered parts and every offered option's text, both questions), option probabilities, selected and executed options with a summary of the native windows, visible native events and native outcomes (`diagnosis_inputs.py`). Use neutral episode ids and the shared 9,000-estimated-token renderer budget; times are native frames (30 per second). Keep the answer-bearing index, file paths, checkpoint ids, experiment metadata and internal native state outside the diagnostic request. Reserve space for the opening and terminal decisions and selected/executed mismatches. [Shared trace contract #168](https://github.com/HectorHHZ/llm-honing/issues/168)

`probe` uses the same rendered trace and also receives results for the first four available model decisions of every episode: the exact logged request and the standard re-render from the saved public state, each under both fixed checkpoints, as normalized probabilities of both questions under the stable names `reference` and `alternate`, plus whether the re-render changed the request. Raw requests, replies and identities stay private for scoring and audit. Same-checkpoint replays are compared with the logged probabilities using the #170 tolerance and tie threshold 0.01 before any probe is used. Identity checks and weight probes are reported separately. [Shared probe #170](https://github.com/HectorHHZ/llm-honing/issues/170)

The diagnosis model is Codex `gpt-6.2-sol` through the Codex CLI ({{CLI_VERSION}}, on the Codex CLI subscription used for the diagnosis). Each episode and mode starts a fresh, tool-disabled, ephemeral session; the prompt is `diagnosis_prompt.txt` (Griddly's prompt with only the game nouns changed; SHA-256 `{{PROMPT_SHA}}`), the reply must match `diagnosis_schema.json`, and at most two attempts are made per episode (the second only after an invalid reply). The raw replies, attempts, reported token usage and timings are saved; per-call dollar cost is unknown with the CLI subscription, and the provider's immutable model revision is not exposed. A pre-registered variant, reported separately, runs `probe` mode once more with `diagnosis_prompt_probe_variant.txt` (SHA-256 `{{VARIANT_PROMPT_SHA}}`): the same prompt plus one sentence, "A reference-versus-alternate probability difference appears in every episode and is not evidence by itself; only a logged probability that fails to match the reference replay and matches the alternate replay is evidence that the weights were changed." The 80 primary calls run before the 40 variant calls. {{DIAGNOSIS_STATUS}}

On verified changed-component episodes report accuracy, macro-F1, per-class scores, confusion, abstention, coverage and calibration of stated confidence. Report control false positives and costs. Include random, majority and constant baselines, and paired `probe` minus `read` differences with reset-group and fault-instance bootstrap intervals. The small number of distinct faults (one instance per component) and the single route limit those intervals to v0 descriptive evidence.
